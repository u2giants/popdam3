A staging item is never overwritten or edited after it is marked STAGED. Retirement of an item only changes its title suffix to `- retired <ATTEMPT_ID>` after it is no longer needed; it is never deleted before step 11.

Evidence the gate accepts it: `ai-task-gates start --class production` in this worktree printed `"production" may start for effective class "production" in u2giants/popdam3` and listed required gates `exact-resource-and-action-ai-reviewer-approval` and `direct-main-reconciliation`. The gate `ai-task-gates check --before production --reviewer-approval <APPROVE report>` runs at step 7 and again at step 9; its output is pasted into #179.

## Answers to GLM round 3 (v6) and self-review
- Attempt numbering: staging uses a timestamp ATTEMPT_ID, not a counter. A retry generates a new ID; an existing item is never reused (fixes the overwrite risk).
- Crash-window reconciliation: step 0 converges any leftover staging item before anything else (see steps).
- Step 2b claim vs check: the check now covers all of /worksp/ansible (every file, every line), for password-setting patterns (`password`, `password_hash`, `chpasswd`, `usermod -p`, `shadow`, `password_lock`) that reference ai or the managed user; and the host check covers cron, systemd units, /etc/cron.d, root and ai crontabs for the same patterns. The claim is narrowed accordingly: "no Ansible or host-scheduled password setter for ai found by these patterns in these locations". It is not a claim about other systems.
- Self-review, idempotency: every step is safe to repeat. Step 1 discovery is read-only. Step 2 reads state. Step 6 stages a new ID each run. Step 8 is verification plus a session kill whose list is re-derived each run. Step 10 scrubs re-scan each run.
- Self-review, crash windows: (a) after step 7 and before step 9 the host holds the staged value; step 0 detects it and converges. (b) during step 6 a partial staging item may exist without STAGED; step 0 treats it as not usable and abandons it (marked retired, never reused). (c) during step 9 a partial canonical write is detected by the fingerprint check and retried from the full-item diff. (d) during step 10 a partial scrub is re-scanned next run.
- Self-review, claim vs check: each "verified" claim in steps is matched by a concrete check; any consumer with no concrete check is Blocked, never passed.

## Answers to Gemini v8 findings
- Credential construction: no `printf` before a successful read. The value is read first into a 0600 file, checked non-empty and exactly 32 bytes (`wc -c`), then piped with `set -o pipefail`. The file is shredded after use.
- Step 0 ordering: sshd recording and the Tailscale address move into step 0a, before any probe.
- Crash window after promotion: step 0 case (iv) splits: if the canonical fingerprint equals the STAGED fingerprint and the staged value logs in, promotion already happened; the run goes to step 10 and step 11. Only differing fingerprints with both logins are ambiguous (Blocked).
- Host fingerprint: the plan does not compute a hash of /etc/shadow. "Applied on host" is established by the login probe (new value accepted), and the vault check is a vault-to-vault comparison of sha256 of the staged and canonical plaintext values.
- Probes: old-refused is tested at most once per path, only if the remaining budget allows; no faillock or fail2ban state is reset by this plan; if budget is insufficient, the probe is recorded "not tested".
- Gate class: see Scope evidence line; the gate tool is the authority and its output is pasted each time.

## Carried requirements
- Throwaway rehearsal of the vault write (field-only edit, round trip, interruption recovery, fingerprint equality, full-item diff) before any canonical edit. The rehearsal also proves an argv-free input form for `op` writes.
- Full-item diff before and after the canonical write: title, tags, URLs, notes, field labels, field types, passkey presence. Only the password field may change.
- Discovery, paths and names only: value grep over /home /etc /opt /srv /var/lib/docker/volumes /var/log /root /data/coolify /worksp /tmp /var/tmp /dev/shm; docker inspect env by value for running containers; vault LOGIN password fingerprints; cron; systemd user units; sshd logs of successful ai password logins (90 days); shell history paths. Remote machines, Coolify UI, GitHub and off-host backups are not searchable from here and are Blocked with owner.
- Lockout: remaining budget = (faillock deny N) - (current `faillock --user ai` failure tally) - 1, further capped by fail2ban sshd maxretry - 1 when fail2ban is active (cap = N-1 when it is not). Before each probe, recompute the budget; if the planned probes exceed it, STOP Blocked rather than probe.
- Per-port auth: sshd -T -C user=ai,host=<h>,addr=<a> per port (1904, 22). Port with password auth disabled is recorded as such.
- Secret transport: the value reaches ssh only through a 0600 file via `sshpass -f`, or a 0600 FIFO; to `chpasswd` only through a pipe into ssh's stdin; to `op` only through the argv-free form proven in the rehearsal; never argv, env, logs, or chat. Template and temp files are shredded after use.
- Plaintext copies found by discovery are scrubbed and shredded; unreadable backups are listed Blocked.

## Ordered steps
0a. Record `sshd -T -C user=ai,host=<h>,addr=<a>` per port (1904, 22), faillock deny N, the current `faillock --user ai` tally, fail2ban sshd maxretry, the Tailscale IPv4 (`tailscale ip -4` on hetz), and the session list. Ports with password auth enabled are fixed here.
0. Crash-window reconciliation and coordination. (a) Read #179 comments and the coordinator thread for a competing claim; a competing claim STOPS the run. (b) List vault items titled `hetz-ai-ssh - pending rotation - *` not yet retired. For each, read only its notes state marker (never the value). An item whose marker is not `STAGED` is abandoned: retire it, never probe it. For each STAGED item, compare its fingerprint to the canonical field fingerprint. If none exist, continue to step 1. If any STAGED item exists, probe only on the ports step 0a recorded password-enabled (if none, STOP Blocked), one login each (staged value, then canonical value), within the remaining probe budget: (i) canonical logs in, staged does not: the host was not changed; mark that staging item retired and continue. (ii) staged logs in, canonical does not: the host changed and promotion is missing; go to step 9 with that staged value after its gates. (iii) neither logs in: STOP Blocked, Hetzner console (step 2d). (iv) both log in: if the canonical fingerprint equals the STAGED fingerprint, promotion already happened: go to step 10. Otherwise STOP Blocked (ambiguous). (c) Record executor tty, session ID, and `ai-task-gates start --class production` output.
1. Discovery (classified, paths and names only). Any successful ai password login from a source outside the known admin set STOPS the run and triggers a persistence check (authorized_keys, cron, systemd user units, shell rc files, Coolify env) before continuing.
2. (Recorded in 0a.) Confirm the probe cap from the 0a values.
2b. Setter check (scope as stated in Answers): grep all of /worksp/ansible (all file types) plus root and ai crontabs (`crontab -l` for each), systemd units, and /etc/cron.d for password-setting patterns referencing ai or the managed user. Any match STOPS the run as Blocked (the next apply or job would revert the rotation). Output paths and pattern names only.
2c. Other sessions: inspect each other ai session (tty, start time, processes, uncommitted work in its checkout) and record. A session with in-flight work is NOT killed; the run stops Blocked for its owner.
2d. Hetzner console/rescue access verified, or the run stops Blocked with owner.
3. Live proof: the stored canonical value authenticates to 1904 and 22 (where enabled). If it fails, STOP Blocked.
4. Rehearsal on a throwaway vault item (field-only edit, round trip, interruption recovery, fingerprint equality, full-item diff, argv-free write form). If no argv-free write form is proven, STOP Blocked.
5. Prove key login and key-based `sudo -n true` for ai from the admin path.
6. Compute ATTEMPT_ID = `$(date -u +%Y%m%dT%H%M%SZ)-$(openssl rand -hex 3)` first. Then create `hetz-ai-ssh - pending rotation - <ATTEMPT_ID>` ONCE with `op item create ... --generate-password='32,letters,digits'` (value generated inside the vault, never leaves it), set notes marker STAGED in the same creation step, and assert length 32 and charset [A-Za-z0-9] by piping `op read` into `wc -c` and `grep -c` (counts only). No template file is used for this item.
7. Gate: `ai-task-gates check --before production --reviewer-approval <report>`; paste output into #179; must pass. Apply (exact construction; no value in argv): with `set -o pipefail`, `op read "op://vibe_coding/<staging title>/password" > $F` (F a 0600 file under $TMPDIR); require `wc -c < $F` equal to 32 before continuing; then `{ printf 'ai:'; cat $F; printf '\n'; } | ssh -p <PORT_PASSWORD_ENABLED> -i <ADMIN_KEY_PATH> ai@<HOST_ADDRESS> 'sudo -n chpasswd'`; then shred $F. <PORT> is a port recorded password-enabled in step 2; <ADMIN_KEY_PATH> is the key proven in step 5. `chpasswd` consumes `user:password` lines; `sudo -n` requires NOPASSWD, which step 5 proved. Break-glass declared in #179 before this step.
8. Snapshot session list (after all probes of steps 0-3 and this step's probes are counted). Verify new accepted on each enabled path (1904, 22, Tailscale IP from 0a); old refused tested at most once per path, only where the budget allows (else recorded not tested); probes run `true` as a non-interactive command. Then terminate only ai sessions cleared in step 2c; record before/after counts with probe sessions identified by their start times.
9. Gate again: `ai-task-gates check --before production --reviewer-approval <report>`; paste output. Promote the staged value to the canonical password field with the proven argv-free form and full-item diff proof; the vault-to-vault check is sha256 equality between the canonical field and the STAGED item.
10. Scrub only confirmed plaintext copies; shred them; list unreadable backups under Blocked. Check each consumer with its own check. Open the Ansible PR in u2giants/ansible for sshd and password-auth state. Run scripts/test-task-gates.sh in this worktree.
11. Retire the staging item for this ATTEMPT_ID (rename suffix, per Scope) only when every consumer is verified or Blocked with owner, and the canonical sha256 equals the STAGED sha256. Record counts in #179.
