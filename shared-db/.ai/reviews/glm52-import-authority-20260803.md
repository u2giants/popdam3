**1. Is the rule unambiguous field-by-field? Mostly on *direction*, not on *default behavior today*.**

The *direction* is clear: curated wins any field a human deliberately set, and authority is per-field. But two sentences cut both ways:

- **The safe-reading clause collides with clause 3.** "Until such a record exists for a field, the safe reading is that the import does not write that field on an existing row at all; it writes only on INSERT" vs. clause 3's "the import loses that field, even while it wins neighbouring fields on the same row." Clause 3 assumes the import *does* write the unset fields on a matched row (active gap-fill on UPDATE); the safe-reading clause says write *nothing* on UPDATE until a curation-record table exists. The wording "the safe reading is…" also reads advisory, not a hard prohibition. So "what does the importer do on UPDATE *today*, before any curation-record infrastructure exists?" has two valid answers (abstain entirely vs. gap-fill the unset fields). That's the genuine ambiguity.
- **"A row is never wholly imported or wholly curated" is contradicted by "create a new row"** — a brand-new row *is* wholly imported. Fine if read as scoped to matched rows; literally inconsistent.
- ("improvement" is ambiguous in isolation, but "anything a human has deliberately set here" in the same clause resolves it — weak.)

**2. Does a "missing vs. deliberately set" loophole survive? Yes — in the matching/INSERT path, not the field writes.**

The clause closes the *field-level* "it was missing, so I filled it" path well (deliberately-set must be recorded, not inferred; abstain if unsure). But it only constrains writes *on an existing row*. Whether an existing row exists *at all* is left to the importer, and the rule explicitly permits "bring in a record we do not have… create a new row" with **no rule for how "do not have" is judged**. That's the row-level analog of the same loophole: fail to match a curated row → declare it absent → INSERT. The clause even *exempts* INSERT ("it writes only on INSERT"), so the freedom is granted by the rule itself. The matching logic makes it concrete: provenance-ref → code → `lower(name)`, and for properties the code/name lookups are scoped to the **feed's** parent — so a curated property under a *different* curated parent is guaranteed not to match and will be judged "missing." The import can still claim a row (and thus all its fields) was missing rather than deliberately set, via exactly the path the clause never touches.

**3. Overwrite paths the gap analysis misses.** Yes — several, all in curated `core.*` tables or via the match/INSERT logic:

- **`core.taxonomy_source_ref.confidence = 'verified'` (force-set on ON CONFLICT).** A status field. A human who deliberately set confidence to `low`/`disputed`/`rejected` is reset to `verified` every run — textbook "re-status something a human deliberately set." The analysis lists the provenance row as written but never applies the per-field rule to its fields. **Missed violation.**
- **`taxonomy_source_ref.source_code` / `source_name` (unconditional ON CONFLICT overwrite).** Same rename class as the `name`/`code` violations on the core tables, on a `core.*` table, but not separated out as violations.
- **`metadata = metadata || jsonb_build_object('plm_import_source', …)`.** An unconditional field write on UPDATE with no curation record — under the safe-reading clause that's itself a (minor) violation, and it's a **trap for proposal item (4)**: if the per-field curation record is stored in `metadata`, this stamp clobbers it every import. (Also unconsidered: jsonb `||` NULL-metadata behavior — worth verifying.)
- **The claimed "NOT a violation: `code`" is wrong.** `code = coalesce(v_source_code, code)` overwrites a *differing* curated code whenever the feed supplies any code (coalesce returns the feed value whenever it's non-null). That's a rename, which the rule explicitly forbids ("may not… rename"). The analysis even states it "replaces a differing curated code" yet labels it non-violation/low-severity — internally inconsistent with flagging `name` as a violation, since both are unconditional overwrites of a curated scalar.
- **Re-parent mechanism is mis-pinned, and the sibling duplicate mode is missed.** The analysis is right that `licensor_id = parent_core_licensor_id` is a violation, but because the code/name lookups are scoped to `p.licensor_id = parent_core_licensor_id`, those paths *cannot* re-parent (a matched row already has that parent). Re-parent actually happens only via the **provenance-ref match** (the one path not scoped to feed-parent). The flip side — also missed — is that the scoped code/name paths *fail to find* a curated property under a different parent and therefore **INSERT a duplicate** under the feed's parent. So the inconsistent scoping (parent-aware for two keys, parent-blind for provenance-ref) yields two distinct corruption modes depending on which key hits: **re-parent vs. duplicate**.
- **Duplicate-INSERT as an indirect status overwrite (second order).** A missed curated row is INSERTed as a new `status='active'` row, so a human's deliberate `inactive` (or other) curation on the original is defeated — not by overwriting the row, but by spawning a live active duplicate that supersedes it. The cascade then cements it: the provenance ref now points to the duplicate, future runs match the duplicate, and the curated original is orphaned permanently. The analysis treats INSERT as benign ("create a new row" is allowed) and never traces this.
- **`lower(name)` matching can manufacture false matches** — casing-only differences a human considered distinct brands collapse to one identity and get overwritten. Noted as a fact, not flagged as an overwrite risk.

Staging (`plm.*`) and `ingest.raw_record` full-overwrite sit outside curated `core.*` and are plausibly fine as mirrors — but `raw_record` overwrite also destroys the audit/evidence base the "deliberately set must be RECORDED" clause leans on, so it's at least worth a sentence.
