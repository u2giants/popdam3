# Generated-types proof for application-return outcomes

Owner: shared-db maintenance; tracked by #4892. This repairs the generated-types
acceptance blocker for #4855 / u2giants/popdam3#523. The original structural issue
keeps its actual `application_return_to`; no substitute outcome issue is needed.

The canonical `Generate database types` workflow remains the only production
proof producer. A blank `work_issue` still selects the existing preview download
path. For an open, ready structural issue with `generated_types: required`, set
`work_issue` to that original issue. If its destination is a consumer application,
also set `application_commit_sha` to the full forty-character current head of that
repository's default branch. The repository is read from the issue, never an input.
The helper reads GitHub repository identity and the actual default-branch head
before production credentials are used, then re-reads them when writing proof.
A missing, malformed or stale consumer commit refuses the run.

The producer checkout must still be the exact current canonical `main`; the
production identity must still be proved through the bounded Management API read;
the generated schema list stays exactly `public,dflow,plm,core,app,hts_rag`. The existing
cross-repository `SYNC_TOKEN` is used only for bounded read-only GitHub requests;
no token or source payload is published. Lack of access fails closed.

Canonical-return work retains version-one proof and its existing SHA binding.
Consumer-return work emits version two: `producer_repository` and
`producer_commit_sha` identify canonical source, while `application_repository`,
`application_commit_sha` and `application_default_branch` identify the consumer.
The artifact is `shared-db-generated-types-<issue>-<consumer-commit>` and contains
exactly `database.types.ts` and `db-generated-types-proof.json`. Canonical-return
runs keep that name bound to the canonical commit. A canonical-return issue does
not accept the consumer commit override.

Record the existing outcome evidence fields: `generated_types_evidence` points
to this canonical workflow run; `generated_types_artifact_id` and
`generated_types_artifact_digest` pin its exact unexpired artifact;
`generated_types_output_digest` pins the actual generated TypeScript bytes. The
consumer's existing `application_repository` and `application_commit_sha` retain
their original meaning. No new outcome-envelope fields are needed.

Native acceptance independently proves the canonical successful main workflow's
actual SHA/path/event/repository, the live original issue destination, the current
consumer default-branch head, the artifact identity/digest, both proof identities,
production project/URL, schema list, and exact generated bytes. A consumer head
that moved after generation requires fresh proof for the newly delivered head.
A closed issue may be rechecked for idempotent outcome verification; generating
new proof still requires an open issue.

The artifact proves generated schema types, not application deployment or visible
behavior. Production apply and separate authenticated live application evidence
remain mandatory. A types artifact cannot satisfy the live assertion verifier.
Download and deliver the generated contract through the application's normal
reviewed source workflow; never hand-edit generated bytes or push protected main.
