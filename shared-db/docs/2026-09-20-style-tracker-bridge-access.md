## Finding and recommendation
The claimed bridge/RFQ permission defect is NOT demonstrated. Existing authenticated projection is intentional, supported by a settled owner rule, explicit projection design, preserved authenticated grants, the consumer path, and present production catalog. ## Field/role contract
- Anonymous: no SELECT on the bridge view. Live catalog authenticated_select=true, anon_select=false; postgres owner, reloptions null.
- Every signed-in POP user, irrespective of ordinary app role: all Styles source fields projected by r (identity/source metadata, SKU/description/customer/designer/commissioned/UPC/customer SKU/licensing/royalty/status/default vendor/notes/flexible row data/audit timestamps), plus source bridge identity/link/match fields. Source policies explicitly authorize authenticated SELECT USING(true) on BOTH public.style_tracker_rows and plm.style_tracker_item_bridge.
- The same signed-in reader receives bounded canonical display fields: item description, customer name, licensor name, factory name, style-group SKU, ERP style number, designer name, customer ID. No source address/email/phone/private vendor contact expansion exists in the view definition. The serving projection deliberately permits canonical names without core application-role membership.
- The same signed-in reader receives rfq_groups, an array of ONLY id/name/linked_at for exact case-insensitive trimmed RFQ-code matches. Latest name and read-only prior-group history are intentional Styles features. It does not project RFQ costs, quotations, margins, buyer prices, or entire RFQ records. Empty array means no match. Underlying dflow RFQItem and RFQGroup authenticated SELECT=false does not contradict this approved narrow projection.
- Administrative matching review controls in StylesPage remain admin-only; that does not make existing row display or RFQ Group column admin-only. The view does not confer writes to core or dflow source tables. Styles add/update remains open by owner ruling; this investigation proposes no changes to it.
- service_role retains intended SELECT grant from the migration. No claim made about restricting this privileged server role.
