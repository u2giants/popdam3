# Completed foreign claim recovery

Owner: shared-db maintenance issue #4054. This capability repairs the completed #3400 claim #3733 blocking #2873. Ordinary owner release is unchanged. A structural claim remains protected after expiry; this route never impersonates its old owner, edits its worktree, grants application acceptance, or runs a migration. Only the compiled #3400 profile is supported. Additional profiles require a reviewed code change; arbitrary SQL, table names and project references are not inputs.

## Evidence and review

The linked work must be closed with a unique trusted `live_verified` completion record matching the source PR and merge. This proves its recorded completed-shape status, not correctness of historical application acceptance. The source PR must be merged, exactly match the claim branch/head and contain the registered migration. There must be no open PR on that branch. The claim must remain uniquely open, body-digest pinned, nonlegacy, and expired; the caller must have current claim-first session authority distinct from the old owner.

Preserve the foreign tree before action. For this narrowly registered case, exactly one tracked migration has a pending deletion of the published `-- derived-from: none` comment, and there may be no other modified/untracked files. The immutable parentless preservation commit contains only `pending.sql`, `pending.patch`, and `catalog.json`. Those pending bytes must match the current foreign worktree and the reviewed manifest's SHA256 hashes. SQL must equal the separately pinned published canonical migration file at preservation base `36d26a393ec311b416023fd21a543310165e6ca2`, with that one comment removed. That base was published on the claim's source branch after the source merge and is not on main, so it must be contained in that published source branch (fresh main must still contain the manifest main, source merge and reviewed tool); it is distinct from the original merged source PR head, whose grouped DDL was later normalized into one ADD per statement. Do not copy transcripts, raw provider responses or customer data into this public repository. A sanitized catalog capture uses an honestly labeled `captured_at`; it is not the database's observation timestamp.

Merge the tool implementation through the normal assigned review and CI first. Prepare the actual recovery manifest as a regular `config/completed-claim-recovery/<claim>.json` file in a maintenance PR, obtaining an allocator-assigned APPROVE of that exact head and those exact input bytes. Runtime fetches that regular file at the reviewed head; changes to the manifest require a new review. The recovery command explicitly names that review issue, PR and head. The implementation does not accept a prose approval, a local report alone, or an earlier unrelated approval.

The manifest fields are `schema_version` (1), `claim`, `work_issue` (3400), `old_owner`, current session UUID `actor`, `claim_body_sha256`, `source_pr`, `source_head_sha`, `merge_sha`, `main_sha`, `tool_commit_sha`, `preservation_commit_sha`, `pending_sql_sha256`, `pending_patch_sha256`, and `catalog_sha256`, and `preservation_base_sha`. The tool commit must already be merged.

## Administrative main freshness

This action changes claim ownership records, not the database. Main may advance after the manifest review only if fresh main descends from the manifest main, merged source and reviewed tool commit, and the registered recovery implementation and bounded transitive static parser/target/authority/review dependency closure and explicitly seeded carry-forward policy registry remain byte-identical to that reviewed merged tool. Runtime also refuses locally modified recovery code. This rule requires no global promotion freeze. It does not change migration merge, preview or production main-freshness rules. Any main movement during the final mutex-protected closure snapshot refuses and requires fresh revalidation.

## Action and recovery

Run `manage-migration-author-lanes.mjs --recover-completed-claim <claim> --report-file <manifest> --recovery-review-issue <maintenance issue> --recovery-review-pr <PR> --recovery-review-head <exact head>` with `SHARED_DB_SESSION_ID`, `SHARED_DB_AUTHOR_ENGINE=codex`, and protected `SUPABASE_ACCESS_TOKEN` supplied by the existing credential route. Never put credentials in arguments or output. The fixed target Management API call is `read_only: true`, checks installed version and all twelve nullable/no-default column facts, and returns the database's `clock_timestamp()`; wrong targets, missing versions, schema drift or stale observations refuse.

Under the coordination mutex, re-prove all evidence, then create and read back an immutable receipt under `refs/db-claim-recoveries/<version>` before closing the claim. Recheck the claim body/state, linked work, merged source, branch PRs, actual main and foreign bytes immediately before closure. The signed close comment names the current recovery actor and old owner separately. The migration version remains permanently reserved; application acceptance is explicitly false in the receipt.

If closing fails after receipt publication, retry the identical reviewed manifest. Reauthenticate a fresh catalog observation and all other evidence, retain the original receipt timestamp, and require current main to descend from that receipt's main. Conflicting receipt identities refuse. Never hand-close the claim, delete the immutable receipt or clean the foreign worktree as a workaround.
