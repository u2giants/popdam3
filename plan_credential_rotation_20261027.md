# Rotation plan v2 — leaked Supabase sb_secret key + broken AI tester logins (qsllyeztdwjgirsysgai)

## Incident summary

During a live-proof session on 2026-10-27 (~11:57 AM EDT), the full value of
the new-format Supabase API secret key (`sb_secret_…`, field
`SUPABASE_SECRET_KEY`) was printed into the ZCode chat transcript while
inspecting the 1Password item "Supabase Runtime Keys - shared POP database
(production)" (vault `vibe_coding`). Per standing rules the credential is
treated as compromised and must be rotated.

Separately discovered: the stored passwords for all three AI tester accounts
are rejected by production auth (`invalid_credentials`).

v2 of this plan corrects v1's central error (REJECT by stepfun review
20261027T164123): the leaked key IS consumed by live automation. Findings
below are probe-verified on production, not assumed.

## Verified facts (probes run 2026-10-27, read-only)

- Edge functions: `POST /functions/v1/admin-api` with the leaked sb_secret
  passes the auth gate (returns app-level `Unknown action` for a probe
  action) — proving the deployed edge env `SUPABASE_SERVICE_ROLE_KEY` holds
  the leaked key (exact-match in `supabase/functions/_shared/admin-auth.ts`).
- The same probe with the legacy service-role JWT stored in the same 1P item
  ALSO passes (via the `allowVerifiedLegacyServiceRole` verified path), and
  that JWT can select `admin_config` via PostgREST — so the stored legacy JWT
  is alive for PostgREST/edge use (it is rejected only by the auth admin API).
- Railway worker (`apps/worker/src/config.ts`): `SUPABASE_SECRET_KEY` env is
  OPTIONAL and used ONLY as the edge-invocation key for the on-demand admin
  operation `reprocess-metadata` (`apps/worker/src/handlers/metadata-reprocess.ts`);
  it falls back to the legacy JWT, which passes the verified-legacy path.
  Whether Railway's env holds the leaked key is UNKNOWN (both Railway API
  tokens in 1Password item "Railway API" are rejected — see Open item).
- CI workflows use `EXTERNAL_SUPABASE_SERVICE_ROLE_KEY` (legacy JWT class,
  verified working) against PostgREST — unaffected by sb_secret rotation.
- Frontends use the publishable key; agents use AGENT_KEY — unaffected.
- Management API access works via 1Password "Supabase CLI Personal Access
  Token" (`sbp_…`). Edge secret values are write-only via the API; the
  secrets list returns only names.

## Steps (order matters)

1. Reset the three tester passwords (GoTrue admin `PUT /auth/v1/admin/users/{id}`,
   authenticated with the still-valid leaked sb_secret), update their 1P
   items, verify each with a password-grant sign-in.
2. Create a NEW sb_secret (`POST /v1/projects/qsllyeztdwjgirsysgai/api-keys`,
   Management API). Store it in the 1P field (replacing the leaked value).
3. Verify the new key: PostgREST probe + auth admin probe.
4. Update the edge function secret `SUPABASE_SERVICE_ROLE_KEY` to the new key
   (`PUT /v1/projects/qsllyeztdwjgirsysgai/secrets`).
5. Probe the edge gate: new key passes (`Unknown action` reply); leaked key
   now fails (401/403).
6. Revoke the leaked sb_secret (`DELETE /v1/projects/qsllyeztdwjgirsysgai/api-keys/{id}`).
7. Verify: leaked key rejected by PostgREST and auth admin; new key works.
8. Update the 1P item notes with the rotation record.

## Risk and bounded breakage

- If Railway's `SUPABASE_SECRET_KEY` holds the leaked key, the ONLY breakage
  is the on-demand admin `reprocess-metadata` operation (worker → admin-api
  edge call returns 401) until the Railway env is updated. No scheduled job,
  no data path, no frontend is affected; the operation is admin-triggered
  from Settings → Diagnostics and fails visibly with an error message.
- If Railway's env is unset, there is no breakage at all (worker uses the
  legacy JWT, which continues to pass the verified-legacy path).
- Nothing is revoked until the new key is stored and verified (steps 2–3
  precede 4–6), so there is no window without a working key.

## Open item (not blocking rotation)

- Railway env `SUPABASE_SECRET_KEY` cannot be read or updated: both tokens in
  1Password item "Railway API" are rejected by the Railway API (re-verified
  today). Updating it requires a fresh Railway API token, which the session
  cannot obtain without Albert (browser SSO). After rotation, if
  `reprocess-metadata` starts failing with 401, that is the cause and the fix
  is the Railway env update.

## Rollback

Before revoking (step 6), a verified new key is deployed everywhere the old
one is required, so rollback is unnecessary. If any consumer fails
unexpectedly, re-issuing another new sb_secret and re-running steps 3–6 is
the recovery; the leaked key stays revoked.

## Out of scope

- Refreshing the stored legacy `SUPABASE_SERVICE_ROLE_KEY` JWT value (it is
  alive for PostgREST/edge; only the auth admin API rejects it).
- Rotating `EXTERNAL_SUPABASE_SERVICE_ROLE_KEY` (GitHub), Railway's other
  env, or the Railway tokens themselves (tracked as the open item above).
